# 自动签到

设置中的「自动签到」分别为当前站点保存开关和签到方式，默认关闭、默认随机鸡腿。
可以先选择固定 5 个或随机，再开启。手动签到入口保持可用。

Android 使用有网络约束的独立 WorkManager 周期任务，每 6 小时尝试一次。
iOS 使用 BGAppRefreshTask，注册在启动完成之前，并声明 fetch 后台模式和任务标识符。
系统决定后台实际执行时间；两端回到前台、登录状态或签到设置改变时都会补做检查。
iOS 的每个原生页面有独立 composition，前台请求由应用容器的 scope 持有，切换页面不会取消签到。

共享 runner 串行处理前后台请求。签到日期按 Asia/Shanghai 计算；先确认当前账号，
再检查站点的当天签到状态，已有结果就不重复提交。完成回执按站点和账号保留，
进程重启、更换登录 cookie 或来回切换账号不会把同一天当成未签。
站点仍是最终依据：请求响应丢失后，下一次先检查服务器状态再决定是否提交。

每个登录会话每天最多自动尝试 3 次，每次至少间隔 30 分钟。尝试在网络请求前持久化，
因此进程被杀、后台任务过期、账号信息读取失败也不会造成无限重试。
网络失败可退避重试；人机验证或登录失效会暂停，直到浏览器验证或重新登录改变会话。
切换站点会换用该站点的开关和回执，不会沿用另一个站点的自动签到授权。

设置内显示等待、进行中、今日完成、网络失败、需验证、需登录或尝试次数耗尽。
后台签到不申请通知权限；开启自动签到也不依赖通知轮询开关。
签到响应只有明确成功或已知的「今天已完成签到」回复才会被接受，
其他带错误文案的拒绝不会写成成功回执。

验证重点是重复调度、重启恢复、跨北京时间零点、换账号和站点、关闭开关、
会话在请求途中失效、挑战后的暂停、有限重试、丢失响应后的核对，以及取消传播。
这些逻辑在 shared/commonTest 中运行；iOS 调度接线还需在 Mac 上编译和真机验证。
